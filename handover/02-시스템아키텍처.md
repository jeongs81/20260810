# 아키텍처 및 데이터 흐름

## 시스템 다이어그램

```
┌─────────────────────────────────────────────────────┐
│ Raw Sources (회의록)                                  │
│ - 자유로운 텍스트 형식                                  │
│ - 최소 프론트매터 (날짜, 회의체, 주관자)                   │
│ - 팀이 직접 작성                                      │
└────────────────────┬────────────────────────────────┘
                     │
                     │ LLM 처리 (Ingest Phase)
                     │ - 회의 내용 분석
                     │ - 액션 추출
                     │ - Wiki 페이지 생성/업데이트
                     ↓
┌─────────────────────────────────────────────────────┐
│ Wiki (구조화된 액션 중심)                              │
│ ├─ 결정 (Decisions)                                  │
│ ├─ 액션 (Actions)                                    │
│ ├─ 보류 (Pending)                                    │
│ └─ 크로스 레퍼런스 & 요약                              │
└────────────────────┬────────────────────────────────┘
                     │
                     │ 조회 & 참고
                     │ - 이전 결정사항 조회
                     │ - 진행 중인 액션 확인
                     │ - 관련 맥락 파악
                     ↓
┌─────────────────────────────────────────────────────┐
│ 아젠다 생성 (Agenda Generation)                       │
│ - 이전 회의 액션 기반 아젠다 생성                        │
│ - 팀의 의사결정 속도 향상                               │
└─────────────────────────────────────────────────────┘
```

## 핵심 원칙

### 1. SSOT는 Raw에만 존재
- Raw 회의록이 유일한 진실의 원천
- Wiki는 Raw로부터 파생된 뷰일 뿐
- 상태 변경은 **반드시 Raw에서만** 기록

### 2. 액션 중심 설계
- Wiki는 결정/액션/보류 같은 액션으로 구성
- 각 액션의 상태, 담당자, 기한을 명확히
- 상태 변경은 후속 회의록에서만 반영

### 3. 최소한의 구조 강제
- Raw는 팀에 부담을 주지 않는 수준의 구조만
- 프론트매터로 최소 메타데이터만 강제
- 본문은 자유로운 텍스트 허용

## 예상 워크플로우

```
1. 회의 진행
   ↓
2. 팀이 회의록 작성 (Raw + 프론트매터)
   ↓
3. LLM이 회의록 읽고 Wiki 업데이트
   - 결정 추출 & 기록
   - 액션 추출 & 할당
   - 보류 식별
   - 크로스 레퍼런스 생성
   ↓
4. 담당자가 Wiki 검증 (옵션: 승인 게이트)
   ↓
5. 다음 회의 준비 시
   - Wiki에서 이전 액션 조회
   - 완료된 액션 상태 업데이트 (회의록에 기록)
   - 새 아젠다 생성
```
