## 🎯 Wiki 구조 설계 (2차 설계)

### 첫 번째 시도: 회의별 단일 페이지 구조

**생성된 파일:**
- `wiki/2026-04-16-제품주간회의.md`

**구조:**
```markdown
# [회의일] [회의체명]

## 📋 회의 요약
한 줄 요약

## 🎯 결정 (Decision)
### 1. 항목명
- 내용
- 근거
- 약속

## ✅ 액션 (Action)
| 담당자 | 항목 | 마감 | 상태 |
| 박준서 | ... | ... | 열림 |

## ⏸️ 보류 (Pending)
해결되지 않은 항목

## 🔗 관련 항목
다음 회의 안건, 선행 조건
```

**특징:**
- Raw의 자유형식 본문을 구조화된 테이블로 변환
- 액션 상태를 "열림/진행/완료"로 표준화
- Raw의 `[ ]` / `[x]` 체크박스를 상태로 매핑

### 주요 설계 결정사항

**결정 vs 액션 구분:**
- **결정**: 회의에서 확정된 방향성 (예: "PG사는 A사로 선정", "정산 주기는 월 1회")
- **액션**: 수행해야 할 구체적인 과제 (예: "PG사 비교표 작성", "계약 조건 확인")

**상태 추적:**
- Raw의 `[ ]` 체크박스 → Wiki "열림" (미완료)
- Raw의 `[x]` 체크박스 → Wiki "완료" (완료)
- Raw에서 진행 중임이 명시 → Wiki "진행" (진행 중)

**페이지 단위:**
- 현재: 회의별 단일 페이지
- 고려사항: 시간이 지나면서 액션 이력이 많아질 경우 재검토 필요

## ⚠️ 미결정 사항 및 검토 필요

### 1. Wiki 전체 구조
- **현황**: 회의별 단일 페이지로 설계 (첫 번째 회의 시도)
- **대안**:
  - 옵션 A: 회의별 페이지 (현재)
  - 옵션 B: 액션 유형별(결정/액션/보류) 통합
  - 옵션 C: 하이브리드 (액션별 페이지 + 회의 기록 아카이브)
- **결정 필요**: 나머지 회의록 변환 전에 확정

### 2. 액션 상태 업데이트 전략
- **현황**: 후속 회의록에서만 변경 (원칙상)
- **미해결**: Wiki를 어떻게 동기화할 것인가?
  - 자동 스크립트로 동기화?
  - 수동으로 매회의마다 업데이트?
  - LLM 프롬프트에 상태 추적 로직 포함?

### 3. 보류(Pending) 항목 추적
- **현황**: 회의별로 기록 (예: "재무팀 정산 프로세스 확인")
- **미해결**: 보류 항목의 생명주기 관리 방식

### 4. 회의체 분류
- **발견된 회의체**: 제품주간회의, 온보딩개선회의
- **미결정**: 분류 체계, 메타데이터 추가 필요 여부

## 📊 Raw 데이터 특성 분석

### 회의록 형식 (현재 Raw)
- **안건**: 회의 주제 나열
- **본문**: 자유형식으로 논의 기록
- **결정**: "### 결정" 헤더로 명시
- **액션**: "## 액션 아이템" 섹션에 체크박스 형식

### 액션 패턴
```
[ ] 담당자 — 항목 설명 (~마감일)
[x] 담당자 — 항목 설명 (완료)
```

### 관찰된 특징
- 결정 사항이 명시적으로 기록됨
- 보류 항목이 "다음 회의에서 재논의"로 표현됨
- 액션 상태(미완료/완료)가 체크박스로 표현됨
- 담당자 명시, 마감일 포함
