# 1차 설계 결정사항

## 확정된 결정

### 1. 액션 상태 변경의 원천
**결정**: 액션 상태는 **후속 회의록(Raw)에서만** 변경  
**근거**: Wiki는 파생물이므로 자체 상태를 저장할 수 없음  
**영향**: 회의록 작성 시 이전 액션의 완료 여부를 명시해야 함

### 2. Wiki 구조
**결정**: Wiki는 **액션 중심**(결정/액션/보류)으로 구성  
**이유**: 팀의 의사결정과 실행 추적이 목적  
**제외**: 단순 산출물이나 정보성 페이지는 제외 (순수 액션만)

### 3. Raw 회의록 포맷 & 파일명 규약
**결정**: 최소 **표준 프론트매터만 강제**, 본문은 자유로운 형식  
**근거**: SSOT로서 팀에 과도한 구조적 부담을 주지 않기 위함  
**파일명**: `YYYY-MM-DD-[회의체명].md` (예: `2026-07-23-제품주간회의.md`)  
**프론트매터 필수 필드**: `회의일`, `참석`  
**프론트매터 선택 필드**: `출처`, `notion_url`, `가져온시점`

### 4. 아젠다 생성 방식
**결정**: 이전 회의의 **미완료 액션을 기반**으로 새 아젠다 생성  
**프로세스**: Wiki → 조회 (이전 액션/보류) → 아젠다 생성  
**목표**: 팀이 우선순위를 명확히 하고 의사결정 속도를 높임

## 유연한 영역 (TBD)

### 1. Wiki 액션의 구체적 구조화 방식
- **질문**: 결정/액션/보류를 어떤 형태로 표현할 것인가?
  - 옵션 A: 각 액션을 별도 페이지로 관리
  - 옵션 B: 회의별로 액션을 묶어 한 페이지로
  - 옵션 C: 액션 유형별(결정/액션/보류)로 분류
- **예정**: 2차 설계에서 결정

### 2. 회의체 분류 체계
- **현황**: 아직 미정, 향후 팀과 협의하며 유연하게 진행
- **패턴**: 제품주간회의, 온보딩개선회의 등 다양한 회의체 확인
- **예정**: 회의록 패턴 분석 후 분류 체계 수립

### 3. Wiki 검증 및 승인 프로세스
- **질문**: Wiki 업데이트 후 누가 검증할 것인가?
- **옵션**: 자동 생성만 할 것인가, 아니면 승인 게이트를 둘 것인가?
- **예정**: 팀의 운영 역량을 고려하여 결정

### 4. 액션 상태 표현 방식
- **현황**: Raw에서 `[ ]` / `[x]` 체크박스 형식 사용 중
- **검증 필요**: Wiki에서 이를 어떻게 매핑할 것인가?
- **예정**: 상태 추적 전략 수립 필요

## 다음 단계

1. **Wiki 액션 구조 정의** (우선순위: 높음)
   - 결정/액션/보류의 마크다운 표현 방식
   - 액션 추적을 위한 필드 (담당자, 기한, 상태 등)
   - 크로스 레퍼런스 생성 규칙
   - 액션 상태 (열림 → 진행 중 → 완료) 매핑 방식

2. **LLM 프롬프트 설계**
   - Raw → Wiki 변환 규칙
   - 액션 추출 및 분류 로직 (현재 Raw에서 "## 액션 아이템" 섹션 사용)
   - 상태 추적 및 업데이트 방식 (체크박스 형식 [ ] / [x] 처리)

3. **회의체 분류 및 메타데이터**
   - 회의체별 특성 파악
   - 추가 메타데이터 필요 여부 검토
   - 보류(pending) 항목 추적 방식

4. **아젠다 생성 로직**
   - 이전 회의 액션 조회 및 필터링
   - 새 아젠다 구성 방식
   - 자동화 여부 결정
